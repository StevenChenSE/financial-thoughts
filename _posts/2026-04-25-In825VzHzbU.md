## The Challenge: Parsing a Cryptic LTE Modem JavaScript File

When you're building an application that locks into your home LTE modem to pull radio signal strength metrics automatically, you need a capable large language model that can understand convoluted source code and connect the dots reliably. That's the real-world scenario driving this benchmark test.

The challenge? A massive JavaScript file from my LTE modem containing the logic for passing login credentials and requesting radio signal metrics. This file is 8,700 lines of cryptic, boilerplate-heavy code—a genuine stress test for any LLM's context recall capabilities.

Previous testing showed that Gemma 4's mixture-of-experts (MOE) model with 26 billion parameters (4 billion active) struggled significantly. Positional memory recall queries returned truncated data with missing or added lines. But that was an MOE architecture. Could the dense 31B variant perform better? And what about Quen 3.6's dense 27B model, which had shown promise in earlier tests but still had one lingering failure?

This investigation digs deep into architecture differences, memory constraints, and raw benchmark performance to determine which model truly dominates long-context code comprehension.

## Understanding the Architecture: Why It Matters

### Sliding Window Attention in Gemma 4

Both Gemma 4 variants—MOE and dense—employ sliding window attention with a 5:1 pattern. This means for every five local attention layers, there's one global attention layer, and this pattern repeats throughout the model.

The critical limitation: in sliding window attention layers, each token only sees a 1,024-token window in the context. This design dramatically improves inference speed but compromises context recall quality. How does it function at all? The five interleaved global attention layers read the full context and inject summaries back into the residual stream. The pattern becomes: **sharpen locally, gather globally, sharpen locally, gather globally**.

These global layers act as lossy checkpoints, diluted by the local layers positioned between them.

### The Dense 31B Advantage

The dense Gemma 4 31B model contains 60 layers instead of 30, maintaining the same 5:1 sliding window pattern. This architecture provides:

- **10 global attention layers** instead of 5 (double the "snapshots" of context)
- **Residual vectors nearly twice as wide**, carrying substantially more information per checkpoint

If the 26B MOE model scans the context with five blurry snapshots, the dense 31B uses ten sharper ones. This architectural difference should theoretically improve long-context recall significantly.

### Quen 3.6's Gated Delta Innovation

Quen 3.6 takes a fundamentally different approach with gated delta networks. For three out of every four layers, gated delta memory doesn't grow with context length—it's fixed. This means:

- 75% of Quen's layers stay the same size whether processing 4K or 128K context
- Memory consumption remains relatively stable across context sizes
- The result is dramatically improved memory efficiency

## Memory Requirements: The Practical Bottleneck

Memory constraints often determine what's actually runnable, not raw capability. Here's how these models compare when handling 128K context with Q8 KV quantization:

| Model | Context Size | Memory Required |
|-------|--------------|-----------------|
| Gemma 4 26B MOE | 128K | 23 GB |
| Gemma 4 31B Dense | 128K | 38 GB |
| Quen 3.6 27B Dense | 128K | ~24 GB |

The dense Gemma 4 31B requires 15 GB more memory than its MOE counterpart—a substantial difference. On a MacBook Pro, this typically triggers the infamous "red screen of death" with most ML runtimes. However, Llama CPP proved more resilient, continuing to push through despite exploding swap usage to SSD.

Quen's gated delta architecture provides a massive advantage here: the dense 27B model consumes 14 GB less than the dense Gemma 4 31B, making it far more practical for long-context tasks without file splitting.

## The Benchmark: Reproducing Function Code from Massive Files

### Methodology

The test asks models to reproduce the first 20 lines of code following the opening brace of functions from the JavaScript file. Testing covers:

- **16 different functions** sampled across the 8,700-line file
- Evaluation criteria: accuracy, completeness, and hallucination prevention
- Models must avoid drifting, bailing out early, or inventing code

### Quen 3.6 27B Dense: Nearly Perfect Performance

The dense Quen 3.6 required exactly 10 minutes for context prefill—the cost of dense inference. Results showed impressive consistency:

**Strengths:**
- Clean code reproduction across most functions
- Consistently generated 15+ lines per function
- No missing lines and no hallucinations
- Outperformed the previous Quen 3.6 35B A3B MOE benchmark

**The Caveat:**
One function proved troublesome. It contained a long line with a repetitive APN configuration sequence running from 0 to 19. These highly repetitive structural tokens create a known trap for transformers, as they have no natural counter or stopping signal. Quen entered a degenerate loop and couldn't complete the output, requiring exclusion from results.

**Personality Quirk:** The model consistently added function signatures at the first line, even though the prompt requested lines following the opening brace. While not technically a failure for practical use, it demonstrated a "helpful" tendency to anticipate user needs.

### Gemma 4 31B Dense: Split Context Success

Since 38 GB exceeded available memory for 128K context, the benchmark split the JavaScript file into two halves, loading 64K context per session.

**First Half Results:**
- Functions 1-2: Perfect
- Function 3: Early stop after large return statement, but accurate
- Function 4: Perfect
- Function 5: Perfect
- Function 6: **Real failure**—changed what the function returns. The original returned an object with three fields; Gemma returned only the last cmd string, fundamentally altering JavaScript behavior
- Functions 7-10: Mixed results with hallucinations around function names and missing commands

**Pattern Identified:** Failures consistently clustered around functions with huge return statements. The same error appeared in the MOE model—difficulty understanding relationships within the file for these complex structures.

**Second Half Results:** When tested on the remaining functions, Gemma 4 31B continued showing similar patterns.

## Head-to-Head Comparison: Did the Dense Model Win?

### Improvement Over MOE

When running the same split-file test with the MOE 26B A4B model:

| Metric | MOE 26B A4B | Dense 31B |
|--------|-------------|-----------|
| Perfect outputs | Fewer | More |
| Recall accuracy | Baseline | Substantially better |

The dense 31B's doubled global attention layers and additional parameters demonstrably help with verbatim function recall. This confirms the architectural hypothesis.

### vs. Quen 3.6

Despite the improvement, the dense Gemma 4 31B still couldn't match Quen 3.6's performance:

- Quen's gated delta architecture allowed loading the entire file without splitting
- Gemma required halving the context and running two separate sessions
- Quen produced cleaner, more consistent outputs across functions
- Quen's single degenerate loop failure versus Gemma's multiple failures around return statements

**The memory efficiency gap is decisive in practice.** Quen's ability to handle full context in one shot versus Gemma's need for context splitting creates a significant workflow advantage.

## What If Gemma Used Gated Delta?

The speculation is tantalizing: Gemma 4's dense architecture showed clear improvements with more global attention layers. What if Gemma 5 implemented gated delta networks like Quen?

Such a combination could theoretically deliver:
- Dense architecture's improved parameter utilization
- Gated delta's memory efficiency at scale
- Possibly the best of both worlds for long-context tasks

Until that happens, the practical choice remains clear for applications requiring reliable code comprehension across massive files.

## Key Takeaways

1. **Architecture matters enormously for long-context tasks.** Dense models with more global attention layers (Gemma 4 31B) substantially outperform their MOE counterparts (Gemma 4 26B) on verbatim recall benchmarks.

2. **Quen 3.6's gated delta architecture is a game-changer for memory efficiency.** The dense 27B model consumes 14 GB less than Gemma's dense 31B at 128K context, enabling full-file processing without splitting.

3. **Dense inference comes at a speed cost.** Quen 3.6 required 10 minutes for context prefill—dense models pay a significant performance penalty compared to MOE variants.

4. **Repetitive structures trip up transformers.** Both models struggled with functions containing highly repetitive APN configuration sequences, highlighting a fundamental limitation of transformer architectures lacking explicit counters.

5. **For practical code comprehension tasks, Quen 3.6 remains the stronger choice.** Despite one degenerate loop failure, its overall accuracy, memory efficiency, and ability to process entire files make it the preferred model for the LTE modem crawler application.

For anyone building applications that require understanding massive, cryptic source files, the evidence points toward Quen 3.6—though the potential of a hypothetical Gemma 5 with gated delta architecture remains an intriguing possibility for future testing.
