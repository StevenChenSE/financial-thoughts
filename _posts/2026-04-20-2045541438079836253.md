# The Future of Coding: How to "Vibe Code" in Production Responsibly

Eric broke his hand cycling to work. For two months, Claude wrote all his code.

That wasn't a hypothetical future scenario—it was Eric's reality as a researcher at Anthropic, specializing in coding agents. And it forced him to crack one of the most important questions in modern software development: **How do you responsibly hand off your codebase to AI?**

At a recent talk, Eric outlined his framework for what's been dubbed "vibe coding"—not just using AI as a coding assistant, but truly letting go of the implementation details and trusting the model to build. It's a bold vision, backed by hard-won lessons from Anthropic's own engineering practices.

## What Is Vibe Coding, Exactly?

The term gets thrown around a lot, often meaning little more than "using AI to generate code." But Eric pushes for a stricter definition borrowed from Andre Karpathy:

> **Vibe coding is when you fully give into the vibes, embrace exponentials, and forget that the code even exists.**

The crucial part? *Forget the code even exists.* When you're still in a tight feedback loop—reviewing every suggestion, approving every change—that's not vibe coding. That's just using a better IDE.

Vibe coding represents a democratization moment. Before, tools like Copilot and Cursor helped engineers code faster. But vibe coding let non-engineers build entire applications from scratch. Suddenly, anyone could create—regardless of technical background.

The downside was predictable: runaway API costs, mysterious bugs, databases filling with random data. The upside mostly stayed in "low stakes" territory—fun side projects, indie games, weekend experiments.

## Why We Should Care Anyway

If vibe coding works best with toy projects and tanks in production, why does it matter?

Because of the exponential.

**AI capability for coding tasks is doubling roughly every seven months.** Right now, AI can handle tasks that take about an hour. That's manageable—you can review everything it produces. But what happens when AI can generate a day's worth of work? A week's? A month's?

You cannot maintain a tight feedback loop with that scale. The math doesn't work.

Eric draws an analogy that software engineers understand instinctively: **compilers**. Early developers didn't trust them. They'd compile their code, then inspect the assembly output line by line. But that approach became impossible as systems grew. Eventually, you just had to trust the compiler.

Vibe coding is the next evolution of that trust. The question isn't *whether* we learn to give up control—it's *how* we do it safely.

## An Ancient Problem in a New Coat

Here's something that might surprise software engineers: **managing implementations you don't fully understand is not new.**

- How does a CTO oversee an expert in a domain they don't know?
- How does a PM review a feature when they can't read the code?
- How does a CEO verify financial reports when they're not an accountant?

These problems have existed for centuries. We have solutions:

- **Acceptance tests** that pass even without understanding the implementation
- **Product demonstrations** that show whether requirements are met
- **Spot checks** on key data points that build overall confidence

Eric's point is sharp: every manager in the world already delegates to systems they don't fully grasp. Software engineers are just late to this party. We've been comfortable as individual contributors who understand every layer of the stack. That era is ending—not because we want it to, but because the exponential demands it.

The key insight: **forget that the code exists, but never forget that the product exists.** You can let go of implementation details while maintaining rigorous focus on outcomes.

## The One Thing We Can't Yet Delegate

There's a caveat Eric is clear about: **technical debt.**

Right now, there's no reliable way to measure or validate technical debt without reading the code yourself. Most other verification methods—acceptance tests, output inspection, stress testing—give you confidence without needing implementation knowledge. Technical debt is different. It requires expertise to assess.

This means vibe coding in production today isn't for everyone. Non-technical founders trying to build a complete business from scratch? That's dangerous. Without the ability to ask the right questions, you can't be an effective product manager for Claude.

So what's the strategic answer? **Focus on leaf nodes.**

## The Leaf Node Strategy

Think of your codebase as a tree:

- **Leaf nodes** (orange dots): End features, endpoints, isolated functionality. Nothing depends on them. They're unlikely to change or have other systems built on top of them.
- **Trunks and branches** (white nodes): Core architecture, foundational systems, shared infrastructure. This is what other code depends on. Changes here ripple everywhere.

Eric's advice: **Vibe code at the leaf nodes.** If technical debt sneaks in, it's contained. The blast radius is limited. You can afford to be less rigorous about code quality in isolated parts of your system.

**Protect your core architecture.** That's where engineers need deep understanding, careful design, and human-reviewed code. That's where extensibility, flexibility, and maintainability matter most.

The good news? Models are improving. Eric notes that Claude 4 has earned significantly more trust than 3.7. Expect the boundary to keep shifting—more of the stack becoming safe for vibe coding—as models mature.

## How to Actually Succeed: Be Claude's PM

Eric's core principle sounds deceptively simple:

> **Ask not what Claude can do for you, but what you can do for Claude.**

When vibe coding, you're not just prompting—you're acting as a product manager for AI. And product management is about context, requirements, and guidance.

A new employee on their first day can't succeed if you just say "build this feature." They'd need:

- A tour of the codebase
- Clear requirements and specifications
- Understanding of constraints and patterns
- Context about how similar things are built

**That's your job now.** When you vibe code, you're responsible for feeding all that context to Claude.

Eric's workflow often looks like this:

1. **Spend 15-20 minutes** in a separate conversation with Claude
2. **Explore the codebase** together, find relevant files
3. **Build a plan** that captures what you want, which files will change, which patterns to follow
4. **Consolidate everything** into a single comprehensive prompt
5. **Let Claude cook**

Once that investment is made, Claude's success rate is remarkably high. The prep work pays off.

## A Real Example: 22,000 Lines of Production Code

Anthropic recently merged a **22,000 line change** to their production reinforcement learning codebase—a significant portion written by Claude.

How did they do it responsibly?

**The process involved days of human work:**

- Rigorous requirements gathering
- Extensive conversation with Claude about system design
- Treating themselves explicitly as product managers for Claude

**The scope was strategic:**

- Most changes concentrated in leaf nodes—isolated parts where technical debt was acceptable
- Core architecture changes received heavy human review

**Verification was built in:**

- Carefully designed stress tests for stability
- System designed with easily human-verifiable inputs and outputs
- Created "verifiable checkpoints" that didn't require reading all the code

Their biggest concern was stability. By running stress tests over long durations, they could measure reliability without inspecting every line. By designing clear inputs and outputs, they could verify correctness independently.

The result: **equal confidence in the change, delivered in a fraction of the time and effort.** But here's the more profound insight—they didn't just save a week of human time. They changed how they think about engineering.

> When something costs one day instead of two weeks, you start thinking: "Let's just do it."

The marginal cost of software is dropping. That's not just efficiency—it's a fundamental shift in what's possible.

## Key Takeaways

1. **Vibe coding means trusting AI with code you don't fully review**—not just using AI as an assistant. Andre Karpathy's definition emphasizes "forgetting the code exists."

2. **The exponential is coming whether we like it or not.** AI capabilities double every seven months. At some point, reviewing every line becomes impossible. Learning to delegate responsibly isn't optional—it's survival.

3. **Be Claude's PM.** Successful vibe coding requires upfront investment in context, requirements, and guidance. The 15-20 minutes you spend preparing are the most valuable minutes in the workflow.

4. **Focus on leaf nodes.** Let AI handle isolated, independent features where technical debt is contained. Protect your core architecture with deep human understanding and review.

5. **Design for verifiability.** Build systems with testable inputs and outputs, measurable stability, and checkpoint verification. You don't need to read the code if you can prove it works.

The question isn't whether vibe coding is coming. It's whether you'll be ready when the exponential arrives.
