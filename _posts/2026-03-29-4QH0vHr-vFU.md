Most people think OpenClaw has one memory system. It doesn’t. There are two completely different retrieval options: **Memory Core** and **QMD**. And almost nobody understands the difference.

I’m a software engineer, and I’ve dug through the actual architecture. By the end of this article, you’ll know exactly when to use QMD, how to set it up, and why it changes how your agents remember everything.

---

## The Foundation: Memory Is Just Markdown

Before we compare anything, we need to clear up the biggest misconception in OpenClaw:

> Your memory is by default not a database or a plugin. OpenClaw memory is plain markdown files sitting in your agent workspace—and that’s it.

You have two default files:
- **`memory.md`** – your curated long-term memory. Think of it as the agent’s notebook.
- A **`memory/` folder** with datestamped files – these are daily append-only notes.

Whatever gets written to these files is what your agent remembers. If it’s not in here, it doesn’t exist.

Here’s the part most people miss: **memory and memory retrieval are two completely different things.** The markdown files are the source of truth. But how your agent searches those files, how it finds the right piece of information when it needs it—that’s the **retrieval layer**.

And OpenClaw gives you two options.

---

## Memory Core: The Built-In Filing System

Memory Core is the default memory system in OpenClaw. It comes built-in, works out of the box, and for most people, this is where you start.

The easiest way to think about it: your agent’s memory lives in markdown notes. Memory Core acts like the filing system on top of those notes. It scans them, organizes them, and builds a searchable map so the agent can quickly find relevant information later.

It gives the agent two tools:

1. **Memory Search** – the “find me something relevant” tool. The agent can describe what it needs in normal language, and OpenClaw searches memory by meaning, not just exact words.
2. **Memory Get** – the “open exactly this note” tool. It can pull a specific memory file or even a specific section inside that file.

So the simple difference: **search helps the agent discover the right note, and get helps it pull the exact note once it knows where to look.**

Behind the scenes, Memory Core ranks results so the most useful notes rise to the top, and it’s built to stay fast as your memory grows. It also watches your memory files for changes—if your notes get updated, OpenClaw can refresh its index automatically.

That’s why Memory Core is such a solid default. It gives you a real memory system without adding too much complexity.

---

## QMD: The Advanced Search Engine

Now let’s talk about QMD, because this is where OpenClaw gives you a more advanced memory search option.

The easiest way to think about QMD is this: **it doesn’t give you memory files.** Your notes still live in the exact same markdown files. What QMD changes is the search engine. You’re not replacing the filing cabinet—you’re replacing the way OpenClaw searches through it.

QMD is an experimental, local-first retrieval backend. In plain English, this means OpenClaw can hand memory searches off to QMD, and QMD uses a more advanced search pipeline to find results.

Instead of relying on just one search method, QMD combines multiple approaches:
- Keyword matches
- Similarity in meaning
- Reordering results so the strongest matches rise to the top

So the simple version: **same notes, better search options**—but it does involve more setup.

QMD is turned off by default. You have to enable it manually, install QMD separately, and make sure your system has the right SQLite support. That means QMD is usually more interesting once your memory gets larger or once search quality starts to matter more.

---

## How to Set Up QMD

If you want to try QMD, here’s what the setup looks like:

**Step 1 – Understand what you’re changing.**  
You’re not moving your memory into a new system. Your `memory.md` file and your `memory/` folder stay the exact same. What you’re changing is the retrieval backend—basically, the search engine OpenClaw uses to look through those notes.

**Step 2 – Turn QMD on in your OpenClaw config.**  
OpenClaw reads its config from `openclaw.json`. QMD is enabled by setting `"memory.backend"` to `"qmd"`. That tells OpenClaw to use QMD for memory retrieval instead of the default built-in indexer. You can also just tell your main agent to turn this on instead of doing it in the config yourself.

**Step 3 – Install the QMD tool itself.**  
QMD does not come bundled automatically. You need to install it separately and make sure the QMD command is available on the same machine where your OpenClaw gateway is running. The docs show installing it via `pip` or downloading a release directly.

**Step 4 – Confirm with your main agent** that you’re now using QMD as your memory backend, and run checks to make sure it’s working correctly.

That’s it—a fairly simple install.

## QMD vs. Mem: Not the Same Thing

Memory Core and QMD get mentioned in the same conversation a lot, but they’re not exactly the same kind of thing.

**QMD is basically an upgraded search engine for OpenClaw memory.** Your notes still live in markdown files inside OpenClaw. QMD just gives OpenClaw a more advanced way to search through them.

**Mem is broader than that.** Mem is its own memory layer for AI agents and applications. It’s designed to store, search, manage, and serve memories across systems, and it can support things like APIs, SDKs, metadata filters, and even graph-style memory.

The easiest way to think about this:  
- **QMD improves OpenClaw’s built-in memory search.**  
- **Mem is closer to bringing in a separate memory platform.**

If you like OpenClaw’s native markdown memory and just want better retrieval, QMD makes sense. If you want a more independent memory layer that could potentially be shared across tools, agents, or applications, Mem is the kind of system you might want to look at.

This is less about which is better and more about: **how native do you want your memory to be inside OpenClaw vs. how much do you want memory to become its own separate layer?**

---

## One Critical Detail: Embedding Providers

One last really important thing—and this is where a lot of people get tripped up:

> Memory search in OpenClaw needs an embedding provider. In simple terms, that’s what allows OpenClaw to search your memory by meaning, not just by exact words.

If you don’t manually choose a provider, OpenClaw will try to pick one for you automatically. It checks in this order:
1. A local embedding model
2. OpenAI
3. Gemini
4. Voyage
5. Mistral

If none of those are available, memory search stays disabled until you configure it. And that matters because your memory files may still exist, but your agent loses the search layer that helps it find relevant notes by meaning. At that point, the system is much more limited—it can still work with specific memory files directly, but it’s no longer doing true semantic recall.

This is especially important if you’re using Anthropic as your main chat model, because Anthropic is **not** one of the embedding providers OpenClaw uses for memory search. In that kind of setup, you usually need to add a separate embedding provider like Gemini, OpenAI, Voyage, Mistral, a local model, or Llama if you want semantic memory search to work.

The main thing to remember: **your chat model and your memory search provider are not always the same thing.**

## Quick Recap

- **OpenClaw memory is markdown files**—that’s the foundation.
- On top of that, you have two retrieval backends:
  1. **Memory Core** – the default, built-in system.
  2. **QMD** – an advanced, optional search layer.
- If you enable QMD, you also need to make sure you have your embedding model set up correctly.
- Don’t confuse QMD with Mem—they solve different problems.
